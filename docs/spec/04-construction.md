# 该文档是本项目的构建指导和约束文档

> 本版（2026-10-04）对应按 `prototype/` 新原型完成的重构。需求见 02 文档，架构与算法见 03 文档。

## 1. 核心指导思想

1. **纵向切片，逐层演进**：先走通最薄的一条完整链路（从数据输入到页面渲染），再逐步叠加复杂度；
   禁止一次性写出大量未验证的代码。
2. **本地优先与 Token 极俭 (Zero-Token First)**：能由本地代码解决的计算（三维匹配度、缺口聚合、
   分布统计），**坚决不调用 LLM**；AI 生成的大文本**必须持久化本地缓存**，且只在用户点击时生成。
3. **留缝不填缝 (YAGNI 与扩展性平衡)**：支持协议适配器与受控词表扩展，但绝不写「当前不需要」
   的过早优化代码。
4. **必要性优先**：02 文档 §2.3 的五条承重理由对应用户可感知的价值，实现时不得为省事砍掉任何一条。

## 2. 构建顺序与切片计划

本轮重构按 6 个阶段推进（阶段 0 是文档与领域规则的冻结，其余按依赖倒排）：

| # | 阶段 | 交付物 | 本阶段引入的复杂度 |
| --- | --- | --- | --- |
| **0** | **文档与领域模型冻结** | 重写 02（功能需求）与 03（数据模型/算法），拍板「能力从哪来」「分数与明细的关系」「LLM 边界」等 6 个原型未定的问题 | 领域术语、匹配口径、缺口聚合口径 |
| **1** | **领域内核** | `shared/schemas/`（ability / experience / requirement / match / dashboard）+ `shared/domain/`（matching / tiers / gap / snapshot）+ 单测 | 纯函数、可测、零 IO 的打分与聚合内核 |
| **2** | **个人能力资产** | 能力维度词表 + 知识/履历/能力三块 CRUD + 个人信息页 | 受控词表、迁移（只增不删）、新页面骨架 |
| **3** | **设置与 LLM 解析管线** | 多厂商配置 + 全局推理参数 + 提取 Prompt v2（产出要求条目与判词）+ 录入弹窗 | 配置形态迁移、Prompt 注入个人资产、待确认列表 |
| **4** | **岗位模块** | 列表（筛选/排序/卡片）、详情抽屉（逐条对比/重新评估）、分类综合分析（雷达 + 缺口 + 成长路线） | 统一要求条目表、过时检测、SSE 成长路线 |
| **5** | **看板与收尾** | 综合看板（指标/分布/分层/待提升项）、文档 01/04 重写、旧模块清理 | 跨岗位聚合、暂缓项归档 |

### 本轮拍板的 6 个领域决策（原型未定，必须显式定下来）

1. **能力是显式资产，不是模型现编的**：能力条目由用户在个人信息页维护并自评（03 §4.6）。
   跨岗位的「有几个岗位提过这项能力」要落在同一个归一化键上才算得出来。
   （2026-10-06 修订：不再预置 12 个维度，改为从空表生长，见 §7.9。
   2026-10-07 修订：**岗位侧不再往这张清单里写**，收敛改由 Prompt 的候选名清单承担，见 §7.10。）
2. **分数是明细聚合出来的，不是模型给的**：逐条结论（完全匹配/需提升/不匹配）× 重要度（硬性/加分）
   按 03 §4.2 聚合出维度分，再按 0.5/0.3/0.2 得出综合分。模型不直接输出任何分数。
   （2026-10-10 修订：结论口径改为「不匹配只留给完全没有」，等级不够一律「需提升」，
   老数据的未标注等级按「一般」计，见 03 §4.2。）
3. **知识结论永远本地算**：知识条目的 `verdict` 不落库，读取时按知识库与自评等级实时判定
   （2026-10-07 起含等级比对，见 §7.10）。这是「新增一项知识 → 全部分数立刻刷新」和
   单调性不变量的前提。
4. **能力/经验的判词随资产一起失效**：解析时记下个人资产快照，资产一变就提示「建议重新评估」，
   由用户点击触发重判，**不自动重算**。
5. **LLM 只做两件事**：解析岗位（录入时一次性）、生成成长路线（按分类、点击触发、结果缓存）。
   其余全部本地。
6. **存储保留本地服务**：浏览器直连 Anthropic / Ollama 有 CORS 限制，密钥也不该落在 localStorage。
   数据存本机 SQLite，服务只监听 `127.0.0.1`。

## 3. 工程规范与研发原则

### ① 失败必须显性 (Explicit Failures)

* **原则**：绝不允许静默降级。提取失败、JSON 不合法、模型未给结论、数据库写入异常，
  都必须捕获并在 UI 上说明是哪一条失败了，同时记录完整日志。
* **落地**：`JobDraft.warnings` 会把每一次自动修正写出来；未判定的能力/经验条目单独计数并在界面上标注。

### ② 本地优先与成本控制 (Cost & Token Efficiency)

* **原则**：
  1. 三维分数、排序筛选、分布统计、缺口排行、过时检测严禁调用 LLM；
  2. AI 大文本（成长路线）进入页面只读缓存，**无缓存时显示按钮，不得自动请求**；
  3. 专业知识 / 技能与能力 / 项目经验变更时只重算数值，绝不自动重算 AI 文本。

### ③ 依赖倒置：核心业务不绑定特定 LLM 厂商

* 业务代码只依赖 `LLMService` 接口；厂商差异全部收敛在 `server/llm/`。
* 模型标识与地址来自用户配置；更换厂商不需要改业务代码。

### ④ YAGNI（留缝不填缝）

* 支持厂商适配与自定义能力维度，但不写「当前不需要」的代码。
* 02 文档 §5 的暂缓清单在被明确要求前一律不恢复界面。

### ⑤ 数据准确性高于一切

* **归一化只有一处实现**：知识键走 `server/services/skillKey.ts`，能力键走 `abilityStore.resolveAbilityKey`。
* 匹配算法与统计**只读归一化后的键**，不在查询里做大小写或别名处理。
* 「匹配引擎认为已掌握、看板认为缺失」是本项目最危险的静默错误，靠单一口径从根上消除。

### ⑥ AI 内容真实性（禁止编造）

* 成长路线只能基于用户录入的专业知识 / 技能与能力 / 项目经验；素材不足时必须标注「通用参考」。
* 判定 Prompt 明确要求：写不出依据就必须判 `GAP` —— 求职场景里编造内容会直接损害用户。

### ⑦ 变更必须可见 (Visible Feedback)

* 任何写操作都要给出可见反馈。知识变更后显示「影响了 N 个岗位的匹配度」。

### ⑧ 环境与技术栈约定

* Node.js LTS + TypeScript；本地服务 Hono；数据库 SQLite（better-sqlite3 + Drizzle）；前端 React 19 + Vite + TailwindCSS v4。
* **迁移不得悄悄毁数据**：升级过程中不得删除或覆盖用户既有数据；确实需要删列或删表时，先做数据搬迁
  （旧列 → 新列）或确认无主（零读者、零数据），并把这次例外在构建记录里写明（先例见 §7.6 的
  `job_ai_cache`、§7.9 的履历残列）。旧形态配置与新形态并存时按 03 §2.2 兼容读取。

### ⑨ 领域术语表（代码名与 UI 文案各定一套，不得混用）

| 代码名 | 界面文案 |
| --- | --- |
| `PersonalSkill` | 专业知识（区块名）/ 知识项（单条） |
| `PersonalExperience` | 项目经验（区块名与单条同名） |
| `AbilityDimension` / `PersonalAbility` | 技能与能力（区块名）/ 能力维度（界面用词；语义是**用户自有清单**里的条目）、能力自评（等级） |
| `RequirementKind.SKILL / ABILITY / EXP` | 知识要求 / 能力要求 / 经验要求 |
| `MatchVerdict.MATCH / PARTIAL / GAP` | 完全匹配 / 需提升 / 不匹配 |
| `Importance.MUST / NICE` | 硬性要求 / 加分项 |
| `ProficiencyLevel.MASTER / PROFICIENT / INTERMEDIATE` | 精通 / 熟练 / 一般（2026-10-07 起由四档改三档，取消「入门」） |
| `GapPriority.HIGH / MEDIUM / LOW`（+ `KEEP`） | 高优先级 / 中优先级 / 低优先级 / 优势巩固 |
| `JobStatus.NOT_APPLIED…REJECTED` | 未投递 / 已投递待回应 / 面试中 / 已发Offer / 已被拒绝 |

## 4. 质量保证与测试策略

### 4.1 重点测试领域（拒绝盲目追求覆盖率）

1. **匹配与单调性**：分数口径、六档边界（含「每一分都落在唯一且正确的档位」的逐分断言）、
   以及「掌握新知识不会让任何岗位分数下降」的不变量（枚举子集验证）。
2. **缺口聚合**：按岗位去重、经验不进榜、优先级分档、未判定条目不制造虚假缺口、
   **等级不够的知识条目要进榜**（只判「在不在知识键集合里」会漏掉这类）。
3. **解耦回归**：保存/删除岗位后，个人侧三张表必须零变化；岗位侧解析能力名不得新建能力条目
   （`server/services/jobStore.decouple.test.ts` 钉住这两条）。
4. **清理型迁移的判据**：`server/db/migrationCleanup.test.ts` 用原样 SQL 验证 0013 只删
   「从未被自评过」的能力条目——包括被 `job_requirement` 引用的那些。
5. **提取规整**：知识结论必须被丢弃、否定词判定顺序、重复合并取严（含要求等级取更高的一档）、
   每次修正都留 warning。
6. **数据迁移**：旧配置形态能读进新形态且**不丢密钥**（有专门的回归测试）。
7. **筛选与 facets**：facets 不因筛选而坍缩、无分数岗位排最后。

### 4.2 交付自检清单

* `npm run typecheck` 无错；
* `npm test` 全绿；
* 涉及界面的改动要在真实浏览器里过一遍（起隔离实例 + dev server，不能只看代码）；
* 涉及写库的端到端验证**必须用隔离数据目录**：`JOBANALYZER_DATA_DIR=<临时目录> PORT=8799 npx tsx server/index.ts`，
  绝不针对用户日常使用的那份数据做写操作。

## 5. 反模式清单（严格禁止）

1. 在业务代码里直接拼厂商 URL / 模型名 / 密钥（必须走 `LLMService` 与配置层）。
2. 复制一份归一化或打分逻辑到别处（前端也不行）。
3. 把模型的自由文本直接当成结构化数据用（必须经 zod 校验 + 规整）。
4. 未配置模型时让功能整体不可用（除解析与生成路线外都必须能跑）。
5. 自动调用模型（打开详情页、切换分类、刷新看板都不该产生请求）。
6. 静默吞掉错误或返回空对象代替失败。
7. 删除或覆盖用户数据来"修复"状态。

## 6. 单元交付流程与指令执行规范

1. 先读文档与相邻代码，确认口径；
2. 改契约（`shared/schemas/`）→ 改服务（`server/services/`）→ 改路由 → 改界面；
3. 补测试并跑 `npm test`；
4. 起隔离实例做一次真实链路验证；
5. 更新文档（02/03 的口径若有变化必须同步）。

### 7.4 与原型的有意偏差

| 原型 | 实现 | 原因 |
| --- | --- | --- |
| 侧栏底部「数据全量存储于本地浏览器」 | 「本地数据保护」+ 数据在本机数据库 | 实际架构是本地 SQLite + 本地服务，照抄会写成假话 |

### 7.7 系统设置模块的模型语义修正（2026-10-05）

用下来发现原型的设置页把"厂商 / 模型 / 参数"的从属关系弄混了，本轮重新理顺为
**厂商 → 模型 → 参数逐层跟随**：

* **不预置厂商**：`resolveSettings` 去掉厂商预设兜底（`sources` 新增 `none`），
  全新安装会明确报「尚未配置模型服务商」而不是打向某家。预设表保留，但降为"添加厂商时的模板"，
  只在用户点名了厂商时（含旧配置写明 providerId）才用来补地址。`DEFAULT_PROVIDER_ID` 随之删除。
* **「默认厂商」→「当前厂商」**：它本来就是"工具当前调用哪一家"，不是"系统默认选哪家"。
* **参数跟随模型**：`StoredProvider.models` 由 `string[]` 变成 `{ name, temperature,
  timeoutMs, stream }[]`，`StoredGlobalSettings` 整个移除（读兼容：旧的 `global` 折叠为各模型初始参数，
  旧的字符串清单升成对象）。模型下拉只列**当前厂商**的模型，不再跨厂商混在一起。
  新增 `PUT /api/settings/model-params` 取代 `PUT /global`（模型名可能带斜杠，故不放进路径）。
  另外保证**当前模型一定在清单里**：用户可能只填过「默认模型」而从没维护清单，那时它不该在下拉里消失。
* **移除「系统级 Prompt 约束前缀」**：提示词是工具能力的一部分。三个内置提示词
  （`extractJob` / `judgeRequirements` / `categoryRoadmap`）本就写明了"只依据给定素材、严禁编造、
  写不出依据就判 GAP"，用户原本可能要在这个前缀里补的约束，内置的已经有了，因此没有新增提示词内容，
  这条管线整个拆掉。

**密钥字段不再有任何回显入口**（F-7.4）：原来那个眼睛按钮能在界面上把密钥亮出来，是一种泄露途径。
现在已保存的密钥只以掩码出现，掩码就是输入框的**内容**（复制走的也只是掩码），
没有显示/隐藏切换，浏览器的密码查看按钮（Edge 自带给密码框）也一并屏蔽。
要更换必须显式点「更换」，新输入的字符以密码框遮蔽，并带 `autocomplete="new-password"`
以免被浏览器当成账号密码存下来。掩码与待提交的新密钥是两个字段，互不混用——
掩码若混进提交字段，就有被当成密钥存进配置文件的风险。

界面缺陷两条（同一轮修掉）：

* **成功提示永久驻留**：`Feedback` 是受控组件、没有计时器（原型的 `JA.toast` 有 2500ms 自动消失，
  移植时丢了）。现在成功提示 4 秒后收起、**错误提示不自动消失**（原则 ① 失败必须显性）。
* **横幅数值的下伸部被切**：数值行用了 `leading-none`（行盒正好 1em），而字体墨迹约 1.3em，
  配合 `truncate` 的 `overflow:hidden`，`g`、`p` 的底部被切掉，看起来像被下方小标签盖住。
  本项目不加载 webfont，回落到 Segoe UI / 微软雅黑时更明显。改为把行高写进字号类
  （`text-xl/[1.4]`）——**不能单独用 `leading-*`**：tailwind-merge 认为它与 `text-*` 冲突，
  两个类同时出现时只保留写在后面的那个，`leading-snug` 会被静默吃掉。
  顺带把 `SettingsPage` 的 `HeroStat` 与 `ProfilePage` 的 `BannerStat` 两份克隆合并为
  `web/components/HeroPanel.tsx`。

### 7.8 系统设置模块的精简（2026-10-06）

7.7 把"厂商 → 模型 → 参数"的从属关系理顺之后，这一轮把**不该由用户决定的旋钮**一并删掉：
设置页的「模型推理参数」只剩温度一项（表单由三列改为两列）。

* **「响应流式输出」删除**：成长路线只有流式一种方式，逐字呈现就是那一屏的交互，不存在二选一。
  `ModelParams.stream` 移除，`routes/categories.ts` 里原来的 `if (modelParams.stream)` 分支
  连同非流式回退一起删掉，直接 `chatStream`。解析岗位仍是非流式——但那是"结果要整体校验后才能用"
  的实现细节（§4.8），不是给用户选的输出方式，没有动。
* **「请求超时」删除**：这是个只会被配错的旋钮——提取长 JD 与逐字生成整段路线时长差一个数量级，
  一个数管不了两边；用户把它调小，换来的只是"提取莫名其妙失败"。改为按调用路径定死的内部常量
  （`llm/openaiCompat.ts`：非流式对话 60 秒、流式生成 180 秒），沿用「单次生成最大 Token」的先例。
  顺带修掉一个隐性错误：原先那个 60 秒的用户值会盖掉流式本该享有的 180 秒宽限，
  长路线生成有被中途掐断的风险。`ModelParams.timeoutMs` 移除；旧配置里的 `timeoutMs` / `stream`
  读取时忽略、写回时不再产生（两者仍留在 `LegacyGlobalSettings` 的读兼容类型里，仅作占位）。
* **编辑厂商弹窗的提示语删除**：「接口地址与模型名都可以改；密钥只以掩码显示……」整句去掉。
  新增与编辑共用一个弹窗，两处一并消失（API Key 字段自己那行说明保留）。

原型 `prototype/settings.html` 同步删掉「请求超时时间 (秒)」「响应流式打字输出 (Stream Output)」
两个控件（连同 `settings.page.js` / `settings.data.js` 里的读写与种子字段）。
原型其余部分仍是上一代设计：「单次生成最大 Token」「系统级 Prompt 约束前缀」「密钥可见性切换」
等早前已下线的东西还在，属于 §7.4 表里记录的既有的有意偏差。

### 7.9 个人信息模块的三块资产重组（2026-10-06）

个人信息页从「知识矩阵 / 工作经验与履历 / 能力自评」改为**专业知识 / 技能与能力 / 项目经验**，
顺序也调成这三块（技能与能力上移到项目经验之前）。改名不是换皮，三块的数据模型都动了：

* **迁移 0009 / 0010：履历 → 项目经验**。`PersonalExperience` 从「公司 / 岗位名 / 岗位类型 /
  起止时间 / 年限 / 核心成果 / 技术标签」收敛成**项目描述 + 持续时长（月）**两项。
  0009 先把旧列拼成项目描述（`公司 · 岗位（起止时间）` + 核心成果逐行）、把年限 ×12 换算成月，
  全部写进新列；0010 才 DROP 那 7 个旧列。表重建用 `__new_` + `INSERT ... SELECT` + RENAME，
  不用 `ADD COLUMN ... NOT NULL`（旧表有数据时会直接失败）。
* **迁移 0011：能力词表取消预置维度**。12 个预置维度（03 §4.6 旧版表格）整体下线，
  `ability_dimension` 同时删掉 `domain` / `builtin` 两列——没有预置项，就没有「预置/自定义」之分，
  也没有了分组。**仍在岗位要求里被引用的维度保留**（按预置键清单 + `job_requirement` / `personal_ability`
  反查）：删掉它们会让那些岗位的能力条目丢掉受控键，用户即使重新录入同名能力也对不回去。
* **迁移 0009 同时删掉 `personal_skill.category`**：知识领域的录入入口被显式移除，
  看板那一栏也从「知识领域分布」换成「知识熟练度分布」（与能力同口径），字段再无任何读者。
* **关于「迁移不得悄悄毁数据」（原则 ⑧）**：0009/0010/0011 都含 DROP，但判断标准与 §7.6 一致——
  **用户看不见的顺手 DROP 禁止，确认无主后的清理必须显式进行**。项目经验是先搬迁再删列；
  知识领域、分组、预置标记则是因为入口与读者都被显式删除，留着只是死列。这仍是例外，不是放松原则。
* **前端**：三个弹窗各自删掉一句说明文字，并去掉「知识领域」「归属分组」两个录入项；
  专业知识与项目经验的空状态不再放居中按钮（统一用区块右上角那个）。
  顶部横幅改成三栏，与页面三大块一一对应：知识熟练度分布 / 能力熟练度分布（含「未自评」档）/
  项目经验时长概况（项目数 + 累计月数）。
* **Prompt 同步**：`extractJob` / `judgeRequirements` / `categoryRoadmap` 三处注入段的标签
  《我的工作履历》→《我的项目经验》，项目描述在进 Prompt 前把换行压成「；」（换行对模型没有额外含义，
  行数却会线性膨胀）。
* **原型 `prototype/profile.html` 未同步**：它仍是上一代设计的静态参照——区块还叫「技能矩阵与能力储备」
  「工作经验与履历」，履历弹窗还是公司/岗位/类型/起止时间/年限/成果/标签七项，
  而且本来就没有能力自评那一块（§7.4 已把它记为有意偏差）。本轮改的是实现，原型留作对照，不追平。

### 7.10 能力清单解耦与岗位要求等级（2026-10-07）

**问题**：在岗位信息模块录入岗位后，该岗位的能力类要求会自动出现在个人信息页「技能与能力」列表里，
用户被迫逐条选熟练度；删除岗位后这些条目仍然残留。

**根因**：这曾是 §7.9 明文设计的「能力维度从空表生长」——保存岗位时 `requirementRowsFor` 对 ABILITY
条目调用 `resolveAbilityKey`，查不到就 `INSERT` 一条维度；而个人信息页渲染的是 `GET /api/abilities`
返回的**整张词表**。删除岗位只删 `job_post`（要求条目靠外键级联），词表里的维度无人清理。
知识侧不存在该问题：`resolveSkillKeyInDb` 是纯函数。

**改法**：

* **能力清单改为用户自有**。`matchAbilityKey`（由 `resolveAbilityKey` 改名，强化「只读匹配」的语义）
  先按归一化名称命中清单里的同名条目、复用它的键，否则直接返回归一化键——**不再写任何个人侧表**。
  删除岗位因此天然不需要清理逻辑，这条性质由 `jobStore.decouple.test.ts` 钉住。
* **跨岗位命名收敛改由 Prompt 承担**。失去共享词表这个强制收敛器后，提取 Prompt 注入
  **有上限的**候选名（用户清单 ∪ 岗位侧已用过的能力名，前 40 个键）要求模型优先复用，
  否则缺口聚合（03 §4.4）会因模型命名波动而把同一项能力拆成两条。
* **岗位要求带上「要求到什么程度」**：`job_requirement.required_level`（迁移 0012），
  由提取模型填，只对知识/能力两类有意义（经验类恒为 null）。知识结论从二元变为按档位差分级
  （03 §4.2 真值表）；能力条目的要求等级随判词 Prompt 一起送给模型。
* **熟练度由四档改三档**（迁移 0013 的后两条语句）：取消「入门」，已有 BASIC 归入「一般」。
  真实库里当时 0 条技能、0 条自评，实际没有数据需要搬迁。
* **雷达图轴来源同步扩为「用户清单 ∪ 岗位提及过的键」**（03 §4.6）：这一条不做，清理之后
  分类雷达会整块空掉，界面还会说「该方向还没有提取到能力类要求」——那是假话。

**关于「迁移不得悄悄删数据」（原则 ⑧ / N-1）**：0013 删的是 `ability_dimension` 里
**从未被自评过**的条目。这与 §7.6、§7.9 的判据一致，且理由更明确：

1. 无自评行 = 用户从未对它们表过态，它们只是自动化产生的噪音，正是本次要修的 bug；
2. 键可由 `normalizeKey(raw_name)` 复现，用户日后新增同名条目即对回岗位侧的历史条目；
3. 与 0011 的保留规则**相反**——0011 保留「仍被 `job_requirement` 引用」的维度，因为那时键必须
   在词表里存在；解耦后这个前提没了，而「岗位已删、维度还在」的残留也只有不排除引用才能覆盖到。

判据由 `server/db/migrationCleanup.test.ts` 用原样 SQL 回归。**这是显式例外，不是放松原则**——
把它当成惯例，下次就会有人顺手删掉用户真正在意的东西。

**兼容性**：存量 `required_level` 全为 NULL，判定口径与升级前完全一致，没有任何分数跳变。

**未做**（属新功能，不在本轮范围）：解耦后用户在「待提升项」里看到某项能力，没有入口把它一键加进
自己的自评清单，只能去个人信息页手动新增同名条目。若日后要补，形态应是缺口项旁一个按钮。

### 7.11 结论口径与个人信息页的可编辑性（2026-10-10）

**起因**：一轮界面走查反馈。核心是结论口径——用户看不懂「基本满足」与「需提升」的区别，
而界面上真正需要区分的是「有、但不够」与「根本没有」两件事。

**改法**：

* **逐条结论改为三档语义**：`完全匹配`（自评 ≥ 要求）/ `需提升`（自评 < 要求，差几档同判）/
  `不匹配`（这项根本没有）。代码枚举不变（`MATCH / PARTIAL / GAP`），**`GAP` 收窄为「完全没有」**，
  红色只用于「要从零补」。知识侧判定的 `deficit === 1 ? PARTIAL : GAP` 随之简化为
  `deficit <= 0 ? MATCH : PARTIAL`（03 §4.2）。
* **未标注等级按「一般」计**：熟练度没有「未标注」这一档——新录入的项默认「一般」，
  老数据里 `level = null` 的项在分布统计与判定里都按「一般」处理（02 F-1.1）。
  界面显示与判定口径必须一致，否则会出现「卡片上写一般、判定却按已掌握算」。
* **能力 / 经验的判词口径同步**：`extract-job-v11` / `judge-requirements-v3`——程度不够一律 `PARTIAL`，
  `GAP` 只用于「资产里找不到相关证据」。详情里**未判定**的条目改按「需提升」展示（原来借 GAP 展示，
  在旧文案下是「需提升」、换文案后就成了红色的「不匹配」，那是假话）。
* **个人信息页**：专业知识卡片上的熟练度改为一行的三档牌子，点哪档就是哪档（就地改，不必进弹窗）；
  能力行补「修改」按钮，改名走新增的 `PATCH /api/abilities/dimensions/:key`，
  **只改显示名、不改键**（键是岗位条目与自评对齐的依据，见 03 §4.6）；
  本页所有删除按钮改为默认灰（与「修改」同色）、悬停才变玫红。
* **岗位侧版式**：卡片匹配度那一行只留三个分数（缺口明细归深度分析抽屉）；深度分析抽屉里只留对比项，
  岗位信息与四个匹配度都留在卡片上；看板的「待补知识与待提升能力」三档默认收起。

**兼容性与分数影响**：老数据里没标等级的知识项，若岗位要求「熟练 / 精通」，会从「完全匹配」变为
「需提升」（`PARTIAL` 权重 0.5），相关岗位的知识匹配度因此**下降**。这是口径统一（界面早就不该
有「未标注」这一档）的必然结果，不是回归；只有恰好命中「未标注 + 要求高于一般」的项会受影响。

**其它文档**：`01-usageExamples.md` 场景四那句「知识库里没有就是需提升」按新口径改了（旧写法在新文案下
会把「不匹配」说成「需提升」），其余叙述未动。
