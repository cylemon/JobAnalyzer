## 2. 总体需求 (Overview & Core Concept)

### 2.1 产品定位

一个**单机本地**的求职分析工具：用户把自己的专业知识、技能与能力、项目经验录进来，把目标岗位（JD 文本或截图）录进来，
由大模型把岗位拆成一条条要求，再由本地算法算出「这个岗位我差多少、差在哪」，并把跨岗位的共性短板
聚合成一张提升清单。

两个不可让渡的性质：

1. **数据不出本机**：所有岗位与个人资产数据只存在本机；只有「解析岗位」与「生成成长路线」两件事会调用大模型。
2. **算分不花 Token**：匹配度、分布统计、缺口排行全部由本地算法完成，任何时候打开都不产生 API 调用。

### 2.2 数据层级关系与聚合统计

```
个人信息（专业知识 / 技能与能力 / 项目经验）        岗位分类（大模型应用开发 / 后端架构师 / …）
          │                                                   │
          │                                                   ├── 岗位 A ── 要求条目（知识 / 能力 / 经验）×N
          │                                                   ├── 岗位 B ── 要求条目 ×N
          │                                                   └── …
          │                                                   │
          └────► 逐条对比（本地判定知识 / 模型判定能力与经验）◄┘
                                 │
                    ┌────────────┴────────────┐
                    ▼                         ▼
            三维匹配度（知识/能力/经验）    跨岗位缺口聚合（待提升项）
                    │                         │
                    ▼                         ▼
              岗位卡片与详情             综合看板 · 分类综合分析
```

* **要求条目（Requirement）是全项目的原子单位**：一个岗位 = 若干条要求，每条要求带「岗位要求原文」，
  以及（能力/经验类的）「用户情况 + 结论」。匹配度不是模型直接给的一个分数，而是这些条目聚合出来的结果。
* **知识条目由本地判定**：知识名归一化成 `skillKey` 后与个人知识库比对——没有这项就是「不匹配」，
  命中再看等级（自评达到或超过岗位要求即「完全匹配」，低于要求即「需提升」）。
  这让「新增一个知识 → 全部分数毫秒级刷新」成为可能，且保证**掌握新知识不会让任何岗位的分数下降**。
* **能力/经验条目由模型判定**：这两类要求的措辞是自由文本（「具备千万级用户高并发交付经验」），
  本地无法用字符串比对，必须在解析岗位时让模型对照用户的技能与能力清单、项目经验给出结论，并落库缓存。

### 2.3 必要性：为什么现有的 Notion 表格 / Excel + ChatGPT 不够用

1. **JD 是非结构化文本**：一份 JD 里混着薪资、城市、公司、职责、要求、加分项，靠手抄进表格的成本高到没人愿意坚持。
2. **「差在哪」需要逐条对齐**：只有一个总分毫无行动价值。用户需要看到「这条要求我满足 / 这条我等级不够 / 这条我完全没有」。
3. **跨岗位的共性短板才是重点**：单个岗位说「需要 CUDA」不重要，20 个岗位里有 12 个说「需要 CUDA」才值得投入时间。
4. **Token 账要算得清**：把 JD 反复丢给 ChatGPT 对比简历，既贵又不可复现；本地缓存 + 本地计算才能长期用下去。
5. **求职数据的隐私属性**：简历与投递记录是敏感数据，不该为了算一个匹配度而上传到第三方。

### 2.4 明确的非目标 (Non-Goals)

* 不做在线服务、不做账号体系、不做多人协作；不做移动端适配（桌面浏览器优先）。
* 不自动投递、不爬取招聘网站、不做岗位推荐；岗位来源始终是用户自己粘贴或截图。
* 不引入外部向量数据库、不做语义检索（理由见 §5 暂缓清单）。
* 不做「AI 直接给总分」：任何分数都必须能拆解成要求条目，**不允许出现无法解释的分数**。

### 2.5 规模与使用假设

* 单个用户；岗位量级 10²，要求条目量级 10³，个人知识量级 10²。
* 使用节奏：集中录入（一次坐下来录 3–10 个岗位，每个岗位各走一次录入）后反复查看；
  查看频率远高于录入频率 —— 这是"录入时多花 Token、之后全部本地"这一取舍的依据。
* 运行环境：本机 Node.js 服务 + 浏览器；服务只监听 `127.0.0.1`。

## 3. 功能性需求 (Functional Requirements)

### F-1: 个人信息与能力资产 (Profile & Capability Assets)

匹配度的"用户侧"输入，三块互相独立、结构一致（都能增删改、都在同一个页面维护）。

* **F-1.1 专业知识（Skill）**：名称、熟练度等级（`精通 / 熟练 / 一般`，**没有「未标注」这一档**）。
  * 知识名在**写入时**归一化为 `skillKey`（详见 F-3.2），归一化只有一处实现。
  * 知识是唯一能被本地精确判定的资产，因此也是唯一能做到「改完立刻看到全盘变化」的资产。
  * **熟练度默认「一般」**：新增时不必先想清楚等级，但要改就得在三档里选一个。等级在卡片上
    一行三个牌子直接点着改，不必进弹窗。老数据里没标等级的项按「一般」显示、也按「一般」参与判定——
    界面显示与判定口径必须一致（见 F-3.2）。
* **F-1.2 项目经验（Experience）**：项目描述（多行文本，写清做了什么、拿到什么结果）+ 项目持续时长（月）。
  * 项目经验是"经验类要求"的判定素材，也是技能与能力自评的现实依据。
  * 持续时长按项目累计（如「2 个项目 / 20 个月」），用于回答「具备 N 年以上相关经验」这类要求。
    **只保留这两项**：公司、岗位名、岗位类型之类的头衔对判定没有帮助，写清楚项目本身更有用。
* **F-1.3 技能与能力（Ability）**：**能力条目**（如「大模型低延迟调优」「高并发架构设计」）+ 自评等级 + 备注。
  * 这份清单是**用户自己的**：**唯一写入者是个人信息页的新增操作**。解析岗位时**只读匹配**
    （同名则复用同一个键），绝不新建条目——否则每录一个岗位，个人信息页就多出一批待自评项，
    删掉岗位也清不掉（2026-10-07 修订，见 04 文档 §7.10）。
  * 清单**不预置任何条目**，从空表开始；用户不需要的条目可以删除，删了之后岗位侧的历史条目保留，
    日后新增同名条目即可对回它们。
  * 每条可以**改名**（如改错别字）：只改显示名，**键不动**——键是岗位侧条目与自评对齐的依据，
    跟着名字改会让已经录入的岗位对不回这项能力（见 03 文档 §4.6）。
  * 跨岗位的「有几家提过这项能力」（F-6.4）改由**归一化键 + 提取 Prompt 的候选名清单**收敛：
    用户清单里的名字与岗位侧已用过的名字会回注给模型，要求优先复用（见 03 文档 §4.6）。
* **F-1.4 一致性**：三块资产任意变更后，知识维度的分数立即本地重算；能力/经验维度的既有判定会被标记为
  「已过时，建议重新评估」（零 Token 的提示，不自动重算）。

### F-2: 岗位分类与多模态录入 (Job Categories & Ingestion)

* **F-2.1 分类管理**：可创建、重命名、删除目标岗位分类（如「大模型应用开发」）；分类下仍有岗位时，
  删除前必须显式告知影响范围。录入弹窗内可直接新增分类，无需离开流程。
* **F-2.2 多模态录入**：**一次录入一个岗位**——可粘贴该岗位的原文和/或上传多张截图
  （同一岗位的不同部分，长 JD 常要两三屏才截得全），一并交给大模型结构化提取。
  * 截图三种给法都要支持：点击选择、拖拽，以及**直接从剪贴板粘贴**（截图工具只把图放进剪贴板，
    不该逼用户先存盘）；粘贴文本的默认行为不受影响。
  * 截图解析依赖所选模型支持图像输入；设置页提供**图像能力探测**（真实发一张 1×1 PNG 验证）。
  * 单个岗位最多 4 张截图、单张不超过 5MB、合计不超过 12MB；超限必须在提交前就说明清楚。
* **F-2.3 提取内容**（结构见 03 文档 §3）：公司、职位描述、薪资（文本 + 数值）、地区（城市 + 区/县两级）、
  业务领域（该岗位服务的业务方向）、**要求条目列表**（按知识 / 能力 / 经验三类，每条含重要度、原文
  与**要求等级**）。
  * 要求等级回答「要求到什么程度」（`精通 / 熟练 / 一般`），只对知识、能力两类有意义；
    原文没写程度就留空，**留空只表示「只比有没有」，不会让用户吃亏**（见 F-3.2）。
  * 只提取「对任职者的要求」这一段内容；岗位职责（这个岗位要做什么工作）不提取。
  * 三类要求的划分口径：**知识**＝知道什么（技术、语言、框架、工具、原理），**能力**＝会做什么、是什么样的人
    （后端开发能力、逻辑思维清晰），**经验**＝做过什么（项目 / 实习 / 年限要求）。
  * **一句话里并列的多个知识点或多段经验必须拆成多条**（「熟悉 LangChain、LangGraph、AutoGen、Dify 等任意一种框架者优先」
    拆成 4 条知识；「具备 RAG 知识库搭建、Prompt 工程、大模型应用开发、模型部署调试经验优先」拆成 4 条经验），
    每条的「岗位要求原文」都保留完整的那一句。
  * 薪资按 **K** 报数（8-12K → 8 / 12），服务端统一折算成「元/月」入库；模型只抄了原文没给数值时
    本地按同一口径补算，仍读不出就显性警告，不允许静默留空。
  * 职位描述要写具体（优先职位名称，没有就用一句概括，30 字以内）；业务领域允许依据全部信息归纳，但必须有原文依据。
  * **岗位原链接不在提取范围内**：JD 正文里通常没有链接，让模型硬编只会编出一个看着像的域名。
    该字段由用户在待确认表单里手填（见 F-2.4），入库前统一校验协议（只收 http / https）。
  * **先通读再提取**：提示词要求模型先把图/文里可见的文字完整读一遍（只在内部进行、不输出），
    再据此填字段；并且**不得依赖「某类信息在页面的什么位置」**——每个人截图范围不同，位置是不确定的，
    只按信息自身的内容特征（金额+单位＝薪资、年限+项目＝经验）判断。
* **F-2.4 待确认后再入库**：提取结果先进入待确认列表，用户可核对修改后提交；不得直接静默入库。
  * **公司、地区、薪资必填**：这三项是岗位列表与排序的骨架——没有公司就看不出是哪家，
    没有地区与薪资就没法比较，缺任意一项这条记录都是残的。
    缺失时逐项标红、在按钮行下给一行就地警示（说明还差哪几项），**「确认入库」不可点**；
    服务端用同一份判定兜底。地区至少要给到城市（区/县是加分信息，招聘页常常只写到城市）；
    薪资「原文或数值有其一」即可（模型只给了数值时不该逼用户再抄一遍原文；招聘页写「面议」
    就照抄「面议」，也算填了）。底部另一条 amber 警告只说「模型这次没读到什么」，
    不再重复「请手动补充」——补什么由那条必填警示统一讲。
  * **职位描述、业务领域与岗位原链接允许留空**：页面上确实没有的信息，不该逼用户现编一个；
    原链接也只是「回原网页」的便利入口，用户手上没有（或不想存）时不该被它挡在入库门外。
    留空的字段在岗位列表与详情里直接不显示（不显示「未提供」这类占位文字）。
  * 三类要求各以「N 条知识 / 能力 / 经验要求」按钮呈现，点它就地展开该类明细；
    不在别处另设「查看全部要求」入口。
  * **岗位原链接必须有一个独占一行的文本框**（它是一条完整网址，塞进半栏会被截得看不出指向哪个岗位）：
    提取到的草稿里该字段为空，由用户粘贴或手动输入；只打了域名时失焦自动补 `https://`。
    它是**选填**：留空一样能入库；填对了，列表里点岗位名就能跳回原招聘页。
  * **链接填了就得合规**（只收 http / https，判定与入库契约 `OriginalUrlSchema` 同一份）：
    不合格时该格标红、hint 换成原因、**「确认入库」不可点**，与必填缺失共用同一条就地警示。
    不这样做的话，用户只会收到服务端一句「请求参数校验失败」，看不出是哪一格、为什么。
    这道校验不能因为改选填而免掉——它是唯一会被塞进 `<a href>` 的用户输入。
* **F-2.5 失败必须显性**：解析失败（图片不支持、JSON 不合法、模型超时）必须写清失败原因，
  且原文与截图保留在原处以便直接重试；**禁止**返回空对象让用户以为"这个岗位没有要求"。
* **F-2.6 重复岗位检测**：同分类下已存在「同公司 + 同职位」时给出提示，由用户决定覆盖还是跳过。

### F-3: 三维匹配与逐条对比 (Matching & Comparison)

* **F-3.1 三维匹配度**：知识匹配度 / 能力匹配度 / 经验匹配度，各自 0–100（无法评估时为「—」）；
  综合匹配度 = 三者的加权和，权重 `知识 0.5 / 能力 0.3 / 经验 0.2`，某维度无法评估时按剩余维度重新归一化。
* **F-3.2 计分口径（不得自由发挥，公式见 03 文档 §4.2）**：
  * 每条要求有一个**结论**：`完全匹配 / 需提升 / 不匹配`（代码名 `MATCH / PARTIAL / GAP`），
    对应权重 1 / 0.5 / 0；
  * 每条要求还有一个**重要度**：`硬性要求(MUST) / 加分项(NICE)`，对应权重 0.8 / 0.2；
  * 维度分 = 100 × Σ(结论权重 × 重要度权重) / Σ(重要度权重)；该维度没有任何条目时为「无法评估」。
  * 知识条目的结论由**本地**判定，比对的是「有没有」与「够不够」两件事：
    * 没录入 → **不匹配**（红：这项知识我根本没有）；
    * 录入了、岗位没写程度 → 完全匹配（不比程度）；
    * 都写了就按档位比：达到或超过要求 → 完全匹配；低于要求 → 需提升（差一档还是差两档同判）。
    * 推论：「要求一般」等价于不比较——它是最低档，不会比任何已录入的等级更高。
      真正会扣分的只有「要求熟练」与「要求精通」。
    * **`不匹配` 只留给「完全没有」**：它是红档，必须真的表示「要从零补」。有、但等级不够一律
      是黄色的「需提升」，否则同一个红档里混着「没学过」与「学得不够」，用户分不出该先补哪条。
  * 能力/经验条目的结论由**模型**在录入时判定；能力条目会把要求等级一并送进判词 Prompt，
    让模型把「要求到什么程度 vs 用户自评到什么程度」算进去（程度不够同样判「需提升」，
    「不匹配」只用于资产里找不到相关证据）。
* **F-3.3 单调性约束**：**新增一项知识、或调高某项已有知识的等级**，任何岗位的知识匹配度与
  综合匹配度都不得下降（必须有单元测试保障）。
  老数据里「未标注等级」的项按「一般」计，它的分数与明写「一般」完全一致（见 F-1.1）——
  不存在「不填等级反而占便宜」的中间态。
* **F-3.4 逐条对比必须可见**：岗位详情必须逐条列出三类要求，每条同时给出「岗位要求」原文、
  **要求等级**（写了才显示）与「用户情况」（知识类由本地生成一句话说明差距在哪，能力/经验类用模型的
  判词），以及结论徽章。
* **F-3.5 过时标记**：技能与能力或项目经验变更后，已有的能力/经验类判定显示「个人资产已变更，建议重新评估」，
  由用户点击触发重新判定（消耗 Token），**不得自动重算**。
* **F-3.6 展示口径**：能力/经验维度是模型的判断结果，界面必须标注其来源与判定时间，不得与本地精确计算的
  知识分混为一谈。

### F-4: Token 边界与 AI 缓存 (Token Boundary & AI Cache)

* **F-4.1 只有两件事调用大模型**：
  1. **解析岗位**（录入时，一次性，产出要求条目与能力/经验判定）；
  2. **生成成长路线**（按分类，用户点击时，产出「知识学习路线」与「能力提升路径」）。
* **F-4.2 零 Token 的本地计算**：三维分数、排序筛选、分布统计、缺口排行、过时检测，全部本地完成；
  页面刷新、切换分类、增删知识都**不得**产生任何 API 调用。
* **F-4.3 缓存强制持久化**：模型产出的大文本（成长路线）必须落库，进入页面时优先读缓存；
  **无缓存时显示按钮，不得自动请求**。缓存必须记录模型标识、Prompt 版本与生成时刻的个人资产快照。
* **F-4.4 AI 内容真实性（硬性）**：成长路线只允许基于用户录入的专业知识 / 技能与能力 / 项目经验，
  **严禁编造**用户未提供的经历、项目或数据。素材缺失时必须显式说明「你的项目经验/技能与能力资产不足，
  以下为通用参考」，而不是编一段像样的经历出来。
* **F-4.5 中断不落库**：流式生成中断或失败时不得写入半截内容，保留旧缓存，显式报错并可重试。

### F-5: 岗位模块 (Job Workspace)

* **F-5.1 岗位卡片**：公司、职位描述、薪资、地区、业务领域、岗位分类、录入天数、投递状态、三维匹配度与综合匹配度。
  缺失的字段不占版面（如没有薪资就不显示薪资标签）；职位描述留空时用一句浅色占位文字保住「点开详情」的入口。
  * 综合匹配度按 03 文档 §4.3 的六档着色（满分 / 极高 / 良好 / 中等 / 偏低 / 待提升），六档口径与看板一致。
  * **岗位名是通往原招聘页的入口**：有岗位原链接时，点岗位名直接在新标签页打开原 Job（名字右侧跟一个外链图标）；
    没有地址、或职位描述本身留空时，退回打开深度分析抽屉。
* **F-5.2 筛选与排序**：关键词（公司 / 职位 / 业务方向 / 城市）、分类、城市、状态四个筛选；
  排序支持「综合匹配度 / 已录入天数 / 最低薪资」与升降序切换。
* **F-5.3 投递状态就地下拉**：`未投递 / 已投递待回应 / 面试中 / 已发Offer / 已被拒绝`，
  在卡片上直接切换，切换后立即重排并给出可见反馈。
* **F-5.4 深度分析抽屉**：逐条展示知识 / 能力 / 经验三类要求的对比（F-3.4）。
  * 抽屉里**只放对比项**：岗位名之外的岗位信息（公司、薪资、城市、状态）与四个匹配度都留在身后的
    卡片上——点进来就是要看逐条结论，再铺一遍只会把对比项挤出首屏。
* **F-5.5 综合分析（按分类）**：选中某个分类后可打开分类综合分析：
  1. **能力雷达图**：该分类下高频能力维度的「岗位平均要求」vs「我的当前水平」；
  2. **知识学习路线**与**能力提升路径**：模型生成、本地缓存、手动触发的成长建议。
* **F-5.6 删除**：删除岗位前必须二次确认，并说明该操作不可撤销。
* **F-5.7 多选与批量操作**：每条岗位可单独勾选，支持全选与多选；选中后可**批量删除**或**移动到其它分类**，
  单个岗位的移动走同一条路径。全选只作用于当前列表里看得见的岗位，改变筛选后不再显示的岗位自动移出选择
  （否则批量操作会波及屏幕上根本没显示的记录）。
  * 批量删除必须二次确认，并在确认框里列出岗位名与总数（N-4 说明影响范围）。
  * 移动只改变岗位归属：要求条目、判词与匹配度原样保留。目标分类下已存在同公司同职位的岗位时**整批拒绝**、
    不做半截移动——重复记录会让缺失技能频次翻倍，直接破坏缺口排行（与 F-2.2 的重复检测同一口径）。

### F-6: 综合看板 (Dashboard)

看板是**纯本地聚合**的展示层：所有数字都从岗位与个人资产算出来，不新增任何数据录入。

* **F-6.1 概览指标**：总关注岗位数（含近 10 天新增、超过 20 天未处理）、平均综合匹配度、
  Offer / 总投递转化、待提升项总量（含高优先级项数）。
* **F-6.2 三张分布环形图**：投递状态分布、岗位类型分布、城市分布；图例必须同时给出数量与占比。
  * 状态分布的颜色与岗位卡片的状徽章**共用同一套色板**，不允许出现"同一状态两种颜色"。
* **F-6.3 匹配度分层统计**：按六档给出岗位数量、占比与典型代表企业，并有一条堆叠进度条总览。
* **F-6.4 待提升项**：
  * 聚合口径：跨该分类（或全部）岗位，统计结论 ≠「完全匹配」的知识与能力条目，
    按归一化键（知识走 `skillKey`，能力走条目名归一化后的键）去重计数，得到「N 个岗位提及」。
    **等级不够的知识条目同样是待提升项**——「有这项知识」不等于「够用」。
  * 优先级：按提及岗位数在该类型内的排名分位划分高 / 中 / 低三档（见 03 文档 §4.4）。
  * 支持「全部 / 仅看知识 / 仅看能力」筛选；数量必须由数据算出，不得写死。
  * 高 / 中 / 低三档**默认收起**，点档位标题栏展开——这一屏的主角是上面的统计图，
    展开后每档都是一长列，想细看哪一档再点开。
  * 经验类缺口不进此榜单（经验无法通过"补一项"解决）。

### F-7: 系统设置 (Settings)

* **F-7.1 多厂商 LLM 接入**：**系统不预置任何厂商**，每一家都要用户手动添加；添加时可就主流厂商
  （DeepSeek / OpenAI / 阿里 DashScope / 月之暗面 / 本地 Ollama 等）的预设模板一键填入地址与常见模型名，
  也可完全手填。Base URL、模型名、API Key 均可编辑；密钥只以掩码显示，**没有任何可见性切换**
  （见 F-7.4）、把某一家指定为**当前厂商**（工具只用当前厂商的服务）。
  协议适配器：当前实现为 OpenAI 兼容；Anthropic / Ollama 原生等各新增一个适配器即可（见 03 文档 §1）。
* **F-7.2 连通性测试**：对任一厂商发起真实探测，把过程与结果逐条显示（明确区分网络失败、鉴权失败、模型不存在）。
* **F-7.3 模型推理参数**：**只有 Temperature**（默认 0.2：这里的调用几乎都是结构化提取，
  要的是稳定复现而不是发散）。**参数跟随模型**——
  每个厂商的每个模型各存一套，界面上先选当前模型再调它那套。
  Max Tokens、超时、是否流式输出都**不做成设置项**：输出上限固定为 `MAX_OUTPUT_TOKENS`（只会被配小、
  把长 JD 的解析整次截断），请求超时按调用路径定死为内部常量，成长路线只有流式一种输出方式
  （三者理由见 03 文档 §2.2 / §4.7 / §4.8）。没有面向前端的提示词设置项：
  提示词内置在工具里（见 F-4）。
* **F-7.4 密钥安全**：密钥只存本机（`data/config.json` 或环境变量），界面不得以明文回显；
  任何日志与错误信息中都不得出现密钥。
  **已保存的密钥没有任何"查看原文"的入口**：不提供显示/隐藏切换，浏览器的密码查看按钮一并屏蔽；
  字段展示的就是掩码本身，选中复制得到的也只是掩码。要更换必须显式点「更换」，
  新输入的字符以密码框遮蔽，且不触发浏览器的密码保存。

## 4. 非功能性需求 (Non-Functional Requirements)

### N-1: 系统架构与单机环境 (Architecture & Offline First)

* 本地服务只监听 `127.0.0.1`；所有数据存本机 SQLite 单文件。
* 除大模型调用外，全部功能在断网状态下可用（浏览、筛选、统计、查看既有缓存）。
* 数据迁移**只增不删**：升级过程中不得删除或覆盖用户既有数据。
  * 唯一的例外是**确认无主之后的清理**，且必须显式进行、写清判据与理由（见 04 文档 §3.⑧）。
    2026-10-07 的能力清单解耦就是一次这样的例外：删除的是**从未被自评过**的能力条目，
    它们是旧版「解析岗位时自动落键」产生的自动化噪音（04 文档 §7.10）。

### N-2: Token 消耗与性能控制 (Token Efficiency & Performance)

* 单次录入的 Token 消耗必须与岗位数量成正比，不得随岗位总量增长（禁止把全量岗位塞进 Prompt）。
  * 回注给模型的候选名清单（用户能力清单 ∪ 岗位侧已用过的能力名）**必须有条数上限**，
    否则它会随岗位总量一起膨胀——那就违反了本条。
* 本地计算路径（列表、筛选、统计、缺口聚合）在 10² 量级岗位下 P95 < 100ms。
* 未配置 LLM 时，除「解析岗位」与「生成成长路线」外的功能必须全部可用。

### N-3: 交互与易用性 (Usability & UX)

* 同一位置的信息必须格式一致：页头标题、分区标题、按钮、徽章、空状态在全站共用同一套组件样式。
* 任何写操作（新增 / 修改 / 删除 / 状态切换）都必须给出可见反馈；失败必须说明原因。
* 长耗时操作（解析、生成）必须显示进行中状态，且可中断。

### N-4: 隐私与数据安全 (Privacy & Data Safety)

* 调用模型时只发送必要内容：解析岗位发送 JD 原文与**个人资产的摘要**（知识名 + 能力维度名 + 项目经验摘要），
  不发送与本次解析无关的岗位数据。
* 删除操作一律二次确认；导入导出等批量操作必须在执行前说明影响范围。

## 5. 暂缓清单（当前版本无界面入口，服务端能力与数据保留）

以下能力在上一版中存在，新界面未提供入口。**保留其数据表与接口**（不迁移、不删除），
后续需要时可直接恢复界面，不得在本次重构中顺手删掉。
（唯一的例外是第 6 项，已于 2026-10-10 作为独立决定**显式移除**——逐项都标了最新状态。）

1. **动态字段**（自定义岗位字段，如「接受出差」）。
2. **知识别名管理页**：别名表本身仍服务匹配算法（F-3.2 依赖它），仅移除管理界面。
   *2026-10-10：管理界面已以弹窗形式恢复（个人信息页 →「专业知识」区头的「知识别名」），
   不是独立页面；只做手动增删，不含自动找同义（见第 5 项）。*
3. **进度快照与趋势回顾**：每次知识变更落一条快照、按时间看匹配度变化。
   *2026-10-10 复核：仍无界面，**保持记录**（写入照常）。*
4. **导出与备份**：全量 JSON 导出与自动备份（备份文件仍在生成）。
   *2026-10-10：界面已恢复（设置页「数据资产」），并补齐了它缺的另一半——**整库恢复**
   （含下载备份、从列表或本机文件恢复、恢复前自动留安全副本）。详见 05-architecture-overview.md §5.7。*
5. **语义相似度建议**（本地向量比对找同义知识）。
   *2026-10-10 复核：仍无界面。它是唯一会产生嵌入 Token 的地方，且要先另配一家
   带 embeddings 接口的厂商（当前只配了 chat 侧），所以向量缓存为空是预期状态。*
6. **简历原文**：新的个人资产是结构化的专业知识 / 技能与能力 / 项目经验，简历原文不再是必需素材。
   *2026-10-10：**已移除**（不是暂缓）——它既没进任何 Prompt，也没有界面入口，
   属于纯粹的功能遗留。删掉了路由、契约与 schema 声明；`profile` 表按「迁移只增不删」
   留在库里，要恢复加回定义与路由即可。*

同时明确**不再提供**：简历靶向优化建议（按岗位生成的 AI 大文本）——新界面把 AI 大文本收敛到
「按分类的成长路线」一处，以减少 Token 消耗与缓存复杂度。它的持久化缓存表 `job_ai_cache`
已随迁移 0008 一并删除（该表当时零读者、零数据；详见 04 文档 §7.6）。
